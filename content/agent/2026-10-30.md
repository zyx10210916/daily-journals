# 回路 · 2026-10-30

本期最值得关注的是“完成”一词被进一步拆开了：节点代码返回，不代表它的事件已进入可重放 Session；checkpoint 已读出，不代表恢复状态已一致地发布给所有执行器；token 已经流到浏览器，也不代表最终消息已原子落库。今天三项更新分别在重试、恢复和流式收口处补上这三个间隙。

检索窗口：2026-10-29 09:09 至 2026-10-30 09:16（Asia/Shanghai）。已核查主要 Agent runtime、协议、多 Agent 项目的主分支更新与官方文档，并补查近期原始论文；没有发现同时满足本窗口、新颖性和工程可迁移性要求的新论文。以下三项均为窗口内合并或实质更新的原始工程来源。

## 1. Google ADK：节点重试前，用 FIFO 屏障等待已排队事件真正进入 Session

**来源**：[google/adk-python #7526](https://github.com/google/adk-python/pull/7526)  
**合并日期**：2026-10-29  
**精读建议**：**必读**。这是并行 workflow 中“兄弟节点明明完成却被重跑”的一个非常典型的时序缺口。

### 核心变化

并行 fan-out 中，一个 sibling 已经执行完并把输出放入 Runner 的事件队列，但主循环可能仍在执行插件回调或等待数据库写入。此时另一个节点失败并触发 retry，旧实现会立刻扫描 Session 重建子节点状态；由于完成事件尚未 append，扫描看不到 sibling 已完成，于是再次执行它，邮件、工具调用等副作用可能发生两次。

新实现让 NodeRunner 在重试前向同一 FIFO 队列插入一个不落库、不触发插件、也不向 SSE 输出的 barrier，并等待它被主循环确认。只有 barrier 之前的事件全部 append 完成，失败节点才重新扫描 Session 并开始下一次 attempt。

相比单纯增加 retry delay，这新增的是一个可证明的 happens-before 关系：

**先完成前一轮已排队事件的 Session 提交，再读取 Session 决定哪些节点需要重跑。**

### 工程价值、证据与局限

**来源结论**：问题在 SQLiteSessionService 下窗口更大，但只需 1 ms 的插件回调延迟也能在 InMemorySessionService 复现；非零 initial_delay 只是降低概率。新增回归测试构造一个失败节点和一个已完成 sibling，确认 sibling 只运行一次。PR 报告 workflow 单测通过，两个既有 Windows tool-node 失败可在 main 复现；复现脚本也覆盖 nested sibling 与 50 ms 插件延迟。

**我的工程推断**：retry 不应直接从“任务已取消/失败”跳到“重新扫描”。中间需要一个 settlement phase：停止接纳本 attempt 的新工作，排空已接受事件，等待 Session revision 前进到 settlement barrier，再基于该 revision 生成新 attempt。barrier 是队列提交确认，不是 sleep。

**局限**：屏障只覆盖同一 Runner 进程内、已经进入队列的事件；进程崩溃、外部工具已经成功但事件尚未入队、或 Session backend 永久阻塞，仍需幂等键、outbox 或 reconciliation。它避免 sibling 被当前 retry 误重跑，不提供通用 exactly-once。

### 适用场景

- **Agent runtime**：将 attempt 状态细分为 running、settling、retrying；retry 只能从已确认的 Session revision 启动。
- **工具确认与续跑**：审批或工具结果已经入队时，恢复扫描必须等它落入权威 Session，不能因暂时不可见再次发起调用。
- **sub-agent 编排**：一个 child 失败不应让已完成但结果尚在汇合队列中的 sibling 重新执行。
- **SSE/UI**：barrier 本身属于内部控制事件，不应投影为用户消息；UI 只消费 barrier 前已正式提交的业务事件。

## 2. Microsoft Agent Framework：checkpoint 恢复增加规范化、冲突预检与可重试发布边界

**来源**：[microsoft/agent-framework #9749](https://github.com/microsoft/agent-framework/pull/9749)  
**合并日期**：2026-10-29  
**精读建议**：**必读**；尤其适合做 RuntimeState schema 演进、checkpoint 迁移或并行恢复的人。

### 核心变化

Declarative workflow 中，Topic、Local 等不同 scope 名称可能实际指向同一逻辑状态。旧实现没有在读取、初始化、清空、表达式求值和恢复路径上统一规范化别名，导致恢复后读取旧值、并行 reader 各自排队迁移、或新旧 scope 同键并存时按偶然顺序覆盖。

新实现把恢复拆成更明确的阶段：

1. 在持久化读写、初始化和枚举前解析 canonical scope；
2. 仅迁移能由 declarative metadata 明确归属的 legacy Topic 项；
3. 在任何写入前预检重叠键，遇到歧义直接拒绝，而不是猜最后写入者；
4. 为 canonical ownership 单独保存版本化元数据，使合法的 raw Topic 与 Local 状态可以共存；
5. 恢复发布失败时丢弃排队更新并重新导入 checkpoint，允许下一次 restore 从干净状态重试；
6. 已成功发布的恢复状态不会因后续 index 或 post-load hook 失败而回滚成与 live executor 不一致的旧值。

相比“加载 JSON 后逐项修补”，新增的是一个带冲突检测和明确回滚边界的状态发布协议。

### 工程价值、证据与局限

**来源结论**：PR 报告最终 declarative 测试在 net10.0 与 net472 共 2,498 项通过；多组针对 alias、legacy migration、fan-out、重复 restore、失败发布和后续 hook 失败的测试在旧实现上失败、修复后通过。公共 API 签名未改变。

**我的工程推断**：RuntimeState 的字段改名、scope 合并和版本迁移不应散落在 getter 中。更稳妥的恢复流程是：载入 checkpoint → 规范化并建立所有权 → 全量冲突预检 → 原子发布新 revision → 运行 post-restore hooks。发布前失败可以整体回滚；发布后 hook 失败应记录为新的运行错误，不能偷偷把权威状态倒回去。

**局限**：这是 .NET declarative workflow 的具体迁移，规则较复杂；旧 checkpoint 若同时存在无法判定所有权的同键项，仍要求人工 reconciliation 或新 Session。测试主要是仓库级状态与并发时序测试，不等同于跨进程崩溃、真实远端存储和网络分区下的事务保证。

### 适用场景

- **状态与协议设计**：为字段别名、scope 映射和迁移规则维护 schema_version 与 ownership_version，不以“谁最后被枚举”决定权威值。
- **状态恢复**：恢复需要单一 publish point；失败重试前清除上次未发布的迁移写入。
- **多 Agent 并发**：fan-out reader 只读同一 canonical snapshot，不允许每个 reader 顺手发起竞争迁移。
- **UI 投影**：恢复成功发布前继续显示旧 revision 或 loading；发布后即使 hook 失败，也应展示“新状态 + 恢复后错误”，不能闪回旧快照。

## 3. Cloudflare Agents Streams：把生产者续写、SSE 重放和最终消息提交放入一条持久日志

**来源**：[Cloudflare Agents：Streams](https://developers.cloudflare.com/agents/runtime/capabilities/streams/)  
**更新日期**：2026-10-29  
**精读建议**：**必读**。与昨日的客户端 SSE decoder 修复不同，今天这一项给出了服务端持久流和最终收口的完整实现边界。

### 核心变化

新的实验性 Streams capability 把仍在生成的回复保存为 Durable Object SQLite 中的有序 chunk log。每个 append 同步持久化并获得 sequence number；reader 可从任意 seq 先 replay 历史，再 follow 实时追加。生产者重启后重新 open 同一 stream，会从 durable cursor 继续；已经 completed 或 errored 的流不能被重新打开写入。

SSE 层直接把 chunk sequence 作为 id：EventSource 使用 Last-Event-ID 重连后，从下一个 chunk 回放；追平历史时发出 up-to-date，最终以 done 或带持久化 reason 的 error 收口。UI 因此可以明确区分 replay 阶段和 live 阶段。

最有工程价值的细节是 close({commit, discard:true})：最终消息写入业务表、流标记完成以及临时 chunk 删除在同一个 SQLite 事务中发生。结果只能是“最终消息已保存且临时流消失”，或“commit 抛错、任何状态都没变且流仍可继续”，避免消息已落库但流仍重复回放，或流已删但最终消息丢失。

### 工程价值、证据与局限

**来源结论**：官方文档定义了 streaming、completed、errored 三态，durable cursor、replay-then-follow、up-to-date、done/error、metadata/tag、批量读取和原子 close/commit/discard；旧流不会自动清理，需要应用显式 delete 或在结算时 discard。该能力目前标记为 Experimental。

**我的工程推断**：SSE 不应是唯一事实源，而应是持久 event log 的一种投影。对 Agent 会话，可把“生成中 reply”看成临时聚合：chunk log 负责断线与进程恢复，terminal transaction 将其折叠为最终 message/item，随后删除临时日志。UI reducer 用 stream_id + seq 去重，并在 up-to-date 后才切换到实时动画。

**局限**：实现依赖 Durable Object SQLite；cursor 只证明已保存多少 chunk，不自动恢复不可重放的模型采样或外部工具副作用。生产者仍需自己根据 cursor 设计可恢复步骤。每个 chunk 默认不超过 1 MiB，历史流没有自动 TTL；实验性 API 可能变化，也不提供跨系统 exactly-once。

### 适用场景

- **SSE 流式收敛**：浏览器断线后按 Last-Event-ID 回放，收到 up-to-date 再进入 live；done/error 是持久终态。
- **状态恢复**：生产者从 durable cursor 恢复，而不是从客户端最后渲染位置猜测进度。
- **Agent 会话**：流结束时将临时 chunk 与最终 message 做事务性交接，避免双来源长期并存。
- **sub-agent/UI**：每个 child Run 使用独立 stream_id；tag 只用于分组，不作为唯一标识，父级按 child terminal state 汇合。

## 今天可以尝试的两个工程验证

1. **把 retry 变成三阶段故障注入**：让 sibling 完成副作用后分别阻塞在“事件未入队”“已入队未落 Session”“已落 Session 未 checkpoint”三个位置，再触发另一个节点失败。验证 settlement barrier 只解决第二层，另外两层由 idempotency/outbox 和 checkpoint 协议兜底。
2. **验证流到消息的原子收口**：在 replay 期间断开多个客户端，并在 close 的业务 commit 前后分别注入异常。期望客户端按 seq 幂等追平；commit 前失败时流仍是 streaming，commit 成功后只剩一条最终 message，刷新页面不再重复播放旧 chunk。
