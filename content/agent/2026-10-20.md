## Meta：Thin Orchestrator——让编排器只负责流程与检查

**来源：Engineering at Meta；发布：2026-10-19；核验：2026-10-20。**

[阅读原文](https://engineering.fb.com/2026/10/19/ml-applications/thin-orchestrator-ai-agent-architecture/)

### 核心变化——来源结论

新意主要是生产实现的具体拆分：中枢按固定流程查重、补齐输入、执行可靠性门控，再委派给隔离的领域子 Agent；通过流程模板复用同一组专家，领域知识按需加载。团队报告用 14 个子 Agent 支撑 20 多种工作流。

### 工程价值、证据与局限

团队称配置准备由先前系统的约一天缩短至不足一小时，约三分之二改动无需重大人工修改。这些是团队自述；文章没有给出足以复现的代码、样本量和受控消融，不能将收益全部归因于拆分。

我的判断：它提供了可照着检查的职责边界，但没有提出新的持久化、事件排序或恢复协议，也没有证明上下文隔离等于权限隔离。未知阶段顺序、探索性强的任务，未必适合直接套固定模板。

### 适用场景——我的工程推断

- **会话与 Tool/Task Gate：** 父 runtime 保存 workflow_id、template_version、step 状态；子 Agent 提交结果和证据。确认后，依据已保存的 gate_id 与 step_id 继续原 run_id。原文的前置可靠性检查并未自动解决“确认后续跑同一 Run”。
- **SSE 与 UI 投影：** 由父 runtime 验证子结果后发布权威的 step 状态；子 Agent 的进度流只作为展示信息。这样可减少 UI 把子 Agent 自报成功当成整体完成的机会。原文未给出 SSE 实现。
- **恢复与结果汇合：** 检查点保存阶段、输入摘要和知识版本；恢复时重做必要检查。外部写操作仍需独立的幂等或结果核对机制，不能因为重试的是子 Agent 就认为副作用安全。
- **编排复用：** 先用两个已知流程试验复用同一组 specialists，再决定是否增加新角色；分别记录越界决策、返工与恢复成本。

### 是否值得精读

**选读。** 正在拆主 Agent、设计 sub-agent 输入契约或固定业务流程时值得精读；重点看前置协议、模板复用与上下文装载。若当前重点是断流重放、持久化恢复或权限隔离，本文提供的实现细节不足。

## 带回开发现场

1. 选一条已有确认门的固定流程，列出所有可由代码判断的前置条件，逐项检查它们是否真正由 runtime 执行，并记录拒绝原因；不要只把条件放进提示词。
2. 在子 Agent 已写入外部系统、父 runtime 尚未收到结果时注入故障：恢复后是否先核对副作用，再决定重试？同时检查 run_id、gate_id 和阶段版本能否保持一致。
