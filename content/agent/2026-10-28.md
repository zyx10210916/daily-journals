# 回路 · 2026-10-28

本期最值得关注的是一条完整的恢复链路：**恢复不能只知道“Run 还没有结束”，还必须知道哪个节点已经完成、完成结果是否真正落盘，以及子 Run 是失败、放弃等待，还是仍可能迟到完成。**

三项更新正好对应这三个层次：

- Google ADK：后续 interrupt 续跑时，不能重新执行已经完成的旧节点；
- Microsoft Agent Framework：并行 sibling 失败时，不能把已完成步骤仍在写入的 checkpoint 一并取消；
- Cloudflare Agents：子 Agent 需要独立、可保留的 Run 生命周期，并区分硬失败、主动取消与可恢复的软中断。

检索窗口：2026-10-27 09:25 至 2026-10-28 09:49（Asia/Shanghai）。已检查主要 Agent runtime、协议、多 Agent 项目的主分支与正式文档，并补查近期原始论文；论文侧没有发现同时满足本窗口、新颖性和直接工程可迁移性要求的新条目。以下两项代码修复已进入项目主分支，Cloudflare 条目为 2026-10-27 更新的官方文档；是否进入你的具体依赖版本仍需单独核对。

## 1. Google ADK：后续 interrupt 恢复不再重跑已经完成的节点

- **来源**：[主分支提交](https://github.com/google/adk-python/commit/d0c3af571faf71252a226bbcb4891cb08374d773)；实现说明见 [PR #7554](https://github.com/google/adk-python/pull/7554)
- **日期**：2026-10-27
- **精读建议**：**必读**

### 核心变化

**来源结论：** 一个设置了 `rerun_on_resume` 的节点可以同时发出多个 interrupt，并在其中任意一个得到回答后继续。例如节点同时等待 `approval` 和 `takeover`，收到 `takeover` 后已经输出 `manual` 并完成；下游节点随后再发出 `confirm`。

旧 replay interceptor 在恢复 `confirm` 时，会先看到早先的 `approval` 仍未回答，再根据“节点支持 rerun 且至少已有一个回答”重跑旧节点。结果是：

- 旧节点的非子节点副作用再次发生；
- 同一输出再次发出；
- 下游虽然最终能继续，但执行历史已经重复。

修复增加 `finished_after_resume` 判断：如果节点在最近一次回答后已经完成，并且已有 output、route、transfer，或该节点本来就不要求输出，则直接使用记录的输出和路由 fast-forward；只有仍在等待、需要所有回答，或 `wait_for_output=True` 却没有输出的节点才会重跑。

### 工程价值、证据与局限

这项修复明确了一个很重要的优先级：

**节点完成事实高于它过去留下的未回答 interrupt。**

旧 interrupt 可以继续保留为历史，但不能因为它仍是 open，就推翻节点已经完成的权威状态。对 Tool Gate 来说，这避免了用户处理后续确认时，再次执行已经由“接管”“拒绝”或其他分支结算的旧动作。

新增测试覆盖开启和关闭 resumability 两种模式，并用真实副作用数组验证旧节点只执行一次。PR 报告相关工作流、Agent、工具、flow 和 runner 测试共 6122 项通过、2 项跳过、6 项预期失败；同一子集在 Python 3.11 与 3.13 上通过，并提供了不依赖模型的端到端复现。

局限包括：

- resumable Run fast-forward 时仍会重新发出记录的 output，这是 replay，不是节点再次执行；消费端仍需幂等合并；
- `wait_for_output=True` 且没有结果的节点会继续重跑，这是有意保留的语义；
- 修复阻止节点代码重复执行，但此前已经发起、尚未确认结果的外部副作用仍需幂等键或 reconciliation；
- PR 页面本身未显示为 GitHub merge，但对应改动已通过项目的主分支提交进入仓库。

### 适用场景与工程推断

- **确认后续跑同一 Run：** 为每个节点保存 `node_execution_id / finished_revision / output_ref`。后续确认只推进当前 waiting node，不能重新打开 finished node。
- **Tool/Task Gate：** interrupt 应有 `open / answered / superseded / stale` 状态。节点一旦按某个回答完成，同节点其余互斥 interrupt 应至少标记为 superseded，而不是永久作为恢复条件。
- **事件顺序与 UI：** replay 的 output 应保留原 `event_id` 或明确标记 `replayed=true`，UI 据此恢复投影，而不是再次播放一次“任务完成”动画。
- **sub-agent：** 子任务已经汇合到父节点后，父 Run 的后续 interrupt 不得重新启动同一 child execution；需要重试时应创建新的 attempt/epoch。

## 2. Microsoft Agent Framework：sibling 失败不能取消已完成步骤的在途 checkpoint

- **来源**：[PR #9644](https://github.com/microsoft/agent-framework/pull/9644)
- **日期**：2026-10-27
- **精读建议**：**必读**

### 核心变化

**来源结论：** 并行工作流中，一个步骤已经完成，但它的 checkpoint 可能仍在等待数据库或其他异步存储 I/O。此时另一个 sibling 失败，旧清理逻辑会取消工作流任务，也可能连带取消这次在途保存。

恢复时，存储里没有已完成步骤的记录，于是 runtime 会再次运行它及其副作用。问题是否出现取决于 storage adapter 在哪里 `await`，因此内存测试可能正常，换成真实数据库后才暴露。

修复做了三件事：

1. 每个步骤的 checkpoint save 作为可跟踪任务运行；
2. 框架自身的 sibling failure 或 human-input pause 清理期间，对保存任务及存储创建的后代任务进行保护并等待其结算；
3. checkpoint 内容在步骤完成时同步构造，只把 `storage.save` 放入后台，避免 ready sibling 在保存真正开始前修改共享状态，污染本步骤快照。

与此同时，调用者主动取消与框架内部失败被明确区分：用户取消或外层 timeout 可以取消在途保存，不能让一个挂死的存储写入无限阻塞调用者退出。

### 工程价值、证据与局限

这项变化把“步骤完成”和“可恢复地完成”区分开：

`step returned → snapshot captured → checkpoint persisted → replay-safe`

只有最后一步完成后，恢复才可以安全跳过该步骤。框架内部 sibling 失败不应破坏已经开始的持久化承诺；但调用者明确取消时，可以选择放弃这次承诺以换取及时退出。

测试覆盖三种 storage timing：直接 await、adapter 内创建 task、adapter 内使用 gather；也覆盖步骤执行、失败清理和人工输入 pause settlement 期间的直接取消与 `asyncio.wait_for` timeout。作者报告工作流测试 1304 项通过、6 项跳过、1 项预期失败；新增的 sibling-failure/resume 用例验证成功 sibling 只运行一次。

局限是：

- 这不是进程崩溃或存储故障下的 durability 保证；
- 调用者主动取消仍可能丢弃尚未完成的 checkpoint，这是明确选择，不是 exactly-once；
- 不合作、吞掉 cancellation 或永久挂起的 adapter 仍可能超出框架保证；
- checkpoint 保存成功只能避免重复计算，外部副作用仍需 destination 端幂等；
- 完整 live storage backend 没有在该 PR 中全部重跑，证据主要来自核心测试与聚焦复现。

### 适用场景与工程推断

- **状态恢复：** 不要在 step callback 返回时立刻向外宣称 replay-safe；至少区分 `completed_in_memory` 与 `checkpoint_committed`。
- **并行编排：** 一个 sibling 失败后，应冻结已经完成 sibling 的 snapshot，等待必要 checkpoint 写入，再形成可恢复失败边界。
- **取消协议：** 使用不同原因传播 `framework_failure`、`pause_settlement` 和 `caller_cancel`；不要把所有 `CancelledError` 都解释为同一种终态。
- **工具副作用：** 对不可重复动作，在外部写入前后分别保存 intent 与 outcome；如果 outcome checkpoint 未落盘，恢复必须先 reconciliation，不能直接重放。
- **SSE/UI：** 可以先流式显示“步骤已完成”，但重连后的权威投影应以 committed checkpoint 或最终 snapshot 为准。

## 3. Cloudflare Agents：把 Agent Tool 变成可保留、可重放的独立子 Run

- **来源**：[Cloudflare 官方文档：Agents as tools](https://developers.cloudflare.com/agents/agent-class/agent-tools/)
- **更新日期**：2026-10-27
- **精读建议**：**选读**；正在做持久 sub-agent、后台任务或多 Agent UI 时升为必读

### 核心变化

**来源结论：** Cloudflare 的 `agentTool()` / `runAgentTool()` 不只是把另一个 Agent 包装成同步函数。每个 child 是拥有独立 Durable Object 存储、消息、工具、可恢复流和查看入口的真实子 Agent；父 Agent 保存一个轻量 run registry，用于刷新后重放、UI 展开和清理。

其中几项契约很值得迁移：

- `runAgentTool()` 按 `runId` 幂等，同一个 ID 不会启动重复 child turn；
- completed、error、aborted、interrupted 都会保留，直到显式清理；
- 失败结果区分 `error / aborted / interrupted`，并提供 `retryable`、机器可读 `reason` 和 `childStillRunning`；
- `inspectAgentToolRun()` 返回 `null` 只表示“尚无可确认记录”，不是失败终态；
- detached child 可以通过方法名形式的 durable `onFinish` 回调完成汇合，避免无法跨进程恢复的闭包；
- 正常路径趋向 exactly-once delivery，但崩溃路径是 at-least-once，因此回调必须幂等；
- 父级因预算耗尽而停止等待只是软 `interrupted`。child 如果后来真正完成，系统仍会再次投递真实终态，不能让“放弃等待”掩盖迟到完成。

文档还把 progress 分成瞬时信号和持久 milestone：瞬时进度采用 latest-wins，刷新后从 child run snapshot 恢复；命名 milestone 才进入持久层。

### 工程价值、证据与局限

它把 sub-agent 从“一个返回字符串的工具”提升为独立可观察执行单元，特别适合深度研究、视频生成、批量导入等超出父 turn 时长的任务。

最有价值的是终态语义：父级等待超时、child 失败和用户主动取消不再合并成一个 `error`。UI 可以继续展示仍在后台运行的 child，父 Agent 也可以根据 `retryable` 与原因选择重连、重新派发或向用户报告。

证据是官方实现文档和 API 契约，没有独立性能或故障注入报告。其他局限包括：

- 具体持久性依赖 Cloudflare Durable Objects，迁移到其他 runtime 需要自己实现 run registry、reconcile worker 与保留策略；
- 崩溃路径明确为 at-least-once，业务回调不能假设只执行一次；
- headless `AIChatAgent` child 不能直接使用浏览器提供的 client tool，需改成服务端能力或由父 Agent 中介；
- transient progress 可能被合并或丢失，不能承担计费、审批或业务状态；
- retained child run 需要清理和配额策略，否则长期会话会持续积累状态。

### 适用场景与工程推断

- **sub-agent 编排：** 父级保存 `parent_run_id / child_run_id / tool_call_id / attempt / status`，child 保留自己的消息与 checkpoint；不要把完整 child transcript 塞回父上下文。
- **结果汇合：** `onFinish` 使用 `child_run_id + terminal_revision` 做幂等键；软中断后的迟到完成是新 revision，不是重复消息。
- **取消与重试：** `aborted` 通常不可自动重试；`interrupted` 是否重试取决于原因和 child 是否仍运行，不能只看一个布尔 `failed`。
- **UI 投影：** 通过父级 run registry 恢复 child 卡片；瞬时 progress 只更新展示，durable milestone 和 terminal event 才推进权威状态。
- **上下文控制：** 父模型只接收结构化 summary 和必要 output，详细过程由 drill-in 页面或按需读取提供。

## 今天可以尝试的两个验证

1. **多 interrupt 同 Run 测试：** 一个节点同时发出“审批”和“人工接管”，回答接管后让下游再请求确认。验证旧节点副作用只发生一次、旧审批变为 superseded、replay output 不会让 UI 重复结算。
2. **并行恢复加迟到 child 测试：** 让 sibling A 完成但阻塞 checkpoint 保存，sibling B 随后失败；同时让一个 detached child 因父级预算耗尽先返回 interrupted、稍后再完成。验证恢复不重跑 A，child 完成回调可重复投递但业务只汇合一次，UI 能从 interrupted 收敛到最终 completed。
