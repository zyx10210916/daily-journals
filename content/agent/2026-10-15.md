本期关注两个进一步形式化的边界：恢复时严格对齐 Agent 上下文与执行环境；任务变化则通过可执行契约判断受保护事实、关系和授权结果是否保持不变。

## SPROUT：上下文与环境一起恢复

**日期：v1 提交于 2026-10-09，原简报于本周收录。精读判断：必读。**

### 核心变化

既有分支、反思或重试方法往往只回退对话上下文，或只保存工作目录。SPROUT 把可恢复状态定义为同一边界下的完整执行环境与 Agent 上下文。

每个完整 turn 后，两者绑定为一个 checkpoint handle。恢复时在独立 microVM 中恢复完整文件系统，用 copy-on-write 创建分支；分支选择由 verifier 的失败证据指导。

### 工程价值与证据

原简报记录：在 DeepSWE 上，相比四次独立重跑，SPROUT 在多个模型上取得更高解决率，同时使用其 32%–52% 的 token。训练实验中，相比普通 GRPO，三个长周期编码基准平均领先 13.9 个百分点，单步训练时间减少 39.5%。这些均为论文特定设置下的报告值。

值得迁移的恢复协议包括：

- checkpoint 绑定环境快照、上下文游标、父分支及 verifier 结果。
- 只从环境与上下文一致的完成边界恢复。
- 分支使用独立写层，不能继续修改父分支。
- 后续引导信息与历史前缀分开保存，不能伪装成原始观察。

### 局限与适用场景

实验 harness 禁止后台进程，工具调用同步执行，并假定跨 turn 的持久状态全部位于磁盘。数据库事务、远程 API、邮件发送等外部副作用不能随 VM 一起回滚；生产系统仍需幂等键、补偿事务和 tool receipt。

适合长时间运行的编码或数据处理 Agent、失败后 checkpoint 恢复，以及继承只读前缀、在隔离环境中执行的 sub-agent 分支。对工具确认后的续跑，联合快照提供了参考，但不会自动解决外部授权与副作用。

## 同一任务：用可执行契约界定授权

**日期：v1 提交于 2026-10-10，原简报于本周收录。精读判断：必读。**

### 核心变化

论文把“修改后是否仍是同一任务”拆为四个可执行检查：

1. 数据是否结构有效。
2. 修改是否属于允许的字段或操作。
3. 受保护事实、实体关系和授权结果是否保持不变。
4. 原始目标是否仍可通过至少一种允许路径完成。

更换收款人可能只改几个字符，却已经是另一个任务；禁用一种付款路径则未必改变任务，只要仍有获准的替代路径。

### 工程价值与证据

作者对同一批 14,336 条已存轨迹采用不同有效性规则重新评分。原简报记录：四种 embedding 方案会接受 75%–100% 的任务改变样本，同时拒绝 24%–45% 的有效攻击样本；在一个配置下，未经契约验证的 64 个易受攻击任务，验证后只有 26 个存在成功且有效的攻击。

### 适用场景——工程推断

```text
TaskContract = {
  protected_facts,
  protected_relations,
  authorized_outcomes,
  allowed_mutations,
  accepted_completion_routes
}
```

用户确认工具调用时，批准规范化后的 action contract。确认后继续原 Run 时，要检查受保护事实、授权结果和允许变更；仅绑定 run_id 不足以阻止确认漂移。

它也可用于 sub-agent 目标范围约束、任务劫持检测，以及 UI 展示“你批准的究竟是什么”。

### 局限

契约依赖开发者先结构化重要事实与权限，不会自动发现正确任务定义。开放任务仍需来源追踪、规范化、澄清或人工裁决；实验没有覆盖长期记忆和多 Agent 交互。

## 带回开发现场

1. checkpoint 同时记录 context_cursor、环境快照、事件序号、工具回执、父分支与审批契约摘要；任一不匹配就拒绝原地恢复。
2. 确认前后刻意修改收款对象、资源 ID、金额、范围和完成条件，验证系统能区分允许的续跑与新的语义尝试。
