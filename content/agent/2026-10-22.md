# Agent 工程与研究日报｜2026-10-22

## 本期最值得关注

过去 24 小时里，最值得带回工程现场的不是新的 Agent 抽象，而是三条控制边界被写进了实现：

1. **回退不是删历史**：应先让当前 Run 静止，再以补偿事件恢复权威状态。
2. **批准 ID 不是权限凭证**：批准必须绑定到服务端会话里真实存在且尚未消费的请求实例。
3. **子 Agent 完成不等于父 Agent 必须续跑**：完成通知与唤醒父 Run 应当是两个独立开关。

这三点共同指向一个更稳的运行时原则：**事实事件、授权能力和调度动作必须分层；任何“续跑”都只能由权威状态重新判定。**

检索窗口：2026-10-21 09:53 至 2026-10-22 09:53（Asia/Shanghai）。仅收录已合入主分支、能改变运行时或协议语义的更新；均尚未见于稳定版发布说明。

## 1. Google ADK：把会话回退暴露为可控的 REST 操作

- **来源**：[提交](https://github.com/google/adk-python/commit/b01c5fff5378fed116b6978cb9293909e3c4a5e0)；[回退语义文档](https://github.com/google/adk-python/blob/main/docs/guides/runners/runner/rewind.md)
- **日期**：2026-10-22（合入 main）
- **建议**：**必读**

### 核心变化

ADK 新增会话 rewind 的 REST 端点。它没有直接改写正在运行的会话：若同一 app/user/session 仍有活动 Run，服务端会先发出 abort，唤醒可能阻塞的下一步并等待 Run 收束；十秒内无法停止则返回 409。确认静止后，才调用 rewind 并返回重新加载、脱敏后的 session。

更重要的是底层语义：回退不会删除旧事件，而是追加一条 rewind 标记事件，写入反向 state delta，并把 artifact 恢复成新的当前版本。审计历史仍在，未来模型上下文会忽略目标 invocation 及其后的对话。

### 工程价值、证据与局限

**来源结论**：代码覆盖了运行中断、目标 invocation 校验、404/409 冲突和会话重新加载；提交同时加入大量 API 测试。官方文档明确指出，外部副作用、memory service、app/user 级状态和已消耗的模型调用不会被撤销，artifact 版本也只会继续增加。

**我的工程推断**：这是一种“先建立静止点，再追加补偿事件”的事件溯源实现，适合做可审计的 time travel。SSE 客户端不能把连接断开视为回退完成；应在收到权威 session 快照后切换 epoch，并丢弃旧 epoch 的迟到事件。

局限有三点：当前改动只在 main，尚未形成稳定版；提交说明没有给出真实活动流的端到端验证；活动 Run 登记看起来是进程内机制，多副本部署仍需要共享 lease、分布式取消或 session 级 fencing token。

### 适用场景

- **Agent 会话/状态恢复**：保留不可变事件日志，以补偿事件恢复 session state 和 artifacts。
- **SSE 收敛/UI 投影**：回退开始即终止旧流；UI 以新快照和新 epoch 为准，不在旧增量上反向打补丁。
- **工具确认与续跑**：历史回退不能自动复活已消费的 approval；Gate 记录应独立保存并重新校验。
- **外部副作用**：邮件、支付、数据库写入必须走补偿或人工对账，不能宣称“会话回退等于业务回滚”。

## 2. Microsoft Agent Framework：重复审批 ID 不能改变执行权限

- **来源**：[提交与回归测试](https://github.com/microsoft/agent-framework/commit/02005995380d5a09167e5c43b5d0f88328979145)
- **日期**：2026-10-21（合入 main）
- **建议**：**必读**

### 核心变化

此前审批响应按 approval ID 收集，一个 ID 只保留一个响应；在混合批次被过滤和重排后，较早响应可能遮住较晚响应，甚至让原本已 settled 的重复项被重新分类为 pending。修复后，框架按**响应对象实例**跟踪未决项，把已关闭请求后的响应标为 settled，并在每轮过滤改变 transcript 后重新计算批次，直到不再丢弃响应。

新增回归测试覆盖 non-streaming、streaming 和 Agent 三种路径：没有权威 AgentSession 记录请求时，即使调用方伪造请求、篡改参数或提交共享同一 approval ID 的多个响应，都不得执行工具；已完成历史中的重复响应则保持惰性，不应破坏重放。

### 工程价值、证据与局限

**来源结论**：修复直接落在批准匹配、混合批次重分类和回放测试上，共改动 3 个文件、增加 137 行并删除 10 行。规范仍强调“一次请求最多授权一个响应”，本地审批需要同一权威 session，hosted approval 则走单独路径。

**我的工程推断**：approval ID 只能用于相关性查找，不能充当 capability。真正的授权键至少应包含 session/thread、request occurrence、call_id、规范化 action digest 与消费状态；消费后写 tombstone，重放只读，不再授权。

局限是这次修复针对一个复杂边界条件，没有性能数据，也没有跨进程存储或分布式竞争的证明；若系统允许显式关闭 session binding，安全责任会重新落到应用层。

### 适用场景

- **Tool Gate/Task Gate**：确认后续跑同一 Run 时，从权威 session 取回原请求；不要仅凭客户端回传的 approval ID。
- **SSE/非流式统一**：批准匹配必须在两条输出路径共享同一状态机和回归用例。
- **持久化与恢复**：历史重放要区分 pending、settled、consumed；重复事件不可再次获得执行能力。
- **测试设计**：加入“同 ID 多响应 + 混合 host/tool 批次 + 过滤后重排”的 property/fuzz 用例。

## 3. Deep Agents：把完成通知与父 Agent 唤醒拆开

- **来源**：[AsyncSubAgent webhook PR](https://github.com/langchain-ai/deepagents/pull/7072)；[notify_parent PR](https://github.com/langchain-ai/deepagents/pull/7132)
- **日期**：2026-10-21（均已合入 main）
- **建议**：**选读**

### 核心变化

AsyncSubAgent 新增两个相邻但独立的控制面：

- 可选 webhook：子 Run 完成后由 Agent Server 回调应用，不再要求应用在内存里长期挂 watcher 或持续轮询。
- notify_parent：默认开启，子任务完成可启动一个新 Run 唤醒空闲父 Agent；关闭后，父 Agent仍能在自己下一次模型调用前看到子任务更新，但不会被子任务自动续跑。

PR 明确给出了应用接管的路径：关闭自动唤醒，由后端先附加凭据、登记完成、更新 UI，再通过正常 launch 路径恢复父 Agent。webhook 负责报告事实，notify_parent 决定调度权，二者并不等价。

### 工程价值、证据与局限

**来源结论**：改动复用了服务端已有的 run-completion webhook，并把通知与父级自动续跑配置透传到 start/update async task。两个功能均标记为 beta，尚未进入稳定版发布。

**我的工程推断**：这是多 Agent 汇合里很关键的解耦。若应用需要在恢复父 Run 前做鉴权、状态落库或 UI 收敛，应设置 notify_parent=false，让 webhook 只生成“child completed”事实；后端去重后再决定是否续跑父 Agent。否则 webhook handler 与默认自动唤醒并存，容易生成两个父 Run。

局限是 PR 规模小，未给出重复 webhook、乱序完成、父 Run 已在执行时的冲突证明；生产环境仍需自己定义幂等键、重试策略和 join 条件。

### 适用场景

- **Sub-agent 并发与结果汇合**：为每个 child run 保存 attempt、completion version 和 parent join 条件。
- **状态/UI 投影**：webhook 先更新子任务状态；父 Agent 的 authoritative run 独立推进。
- **父级续跑**：只有满足去重、依赖齐备和父级空闲条件时才发起新 Run。
- **需要中间业务步骤的系统**：例如先审计结果、注入租户凭据或做人工确认，再恢复父 Agent。

## 可以立即尝试的两项改进

1. **引入 Run epoch 与静止屏障**：所有 SSE 事件携带 session_epoch/run_id/seq；回退、恢复或父级重启前先拿 session fence，旧 epoch 的迟到事件只能记录，不能再投影到 UI。
2. **把批准和子任务完成都改成“事实 + 决策”两阶段**：先持久化 immutable fact（approval received / child completed），再由权威会话状态机产生唯一的 execute/resume decision；用 action digest、consumed tombstone 和幂等键阻止重放。
