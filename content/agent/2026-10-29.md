# 回路 · 2026-10-29

本期最值得关注的不是新框架，而是三个运行时边界同时从“静默继续”转向“显式拒绝或等待”：陈旧 Session 不能悄悄覆盖权威状态；计划审批不能在恢复后丢失；SSE 断流不能把网络 chunk 误当事件边界，也不能无声假装游标连续。它们共同指向一个可迁移原则：一旦系统无法证明状态连续，就应暴露冲突、门控或缺口，而不是猜测。

检索窗口：2026-10-28 09:49 至 2026-10-29 09:09（Asia/Shanghai）。本窗口未发现证据与工程可迁移性同时达到收录标准的新论文；以下均为原始项目的合并变更与测试。

## 1. ADK JS：陈旧 Session 写入不再自动重载，而是明确失败

**来源**：[google/adk-js #1182](https://github.com/google/adk-js/pull/1182)  
**合并日期**：2026-10-28  
**精读建议**：**必读**。这是把 Session 权威性从“最佳努力同步”提升为可验证并发契约的典型小改动。

### 核心变化

此前，DatabaseSessionService.appendEvent 发现数据库中的 Session 比调用方持有的对象更新时，仍会落事件，并将内存状态重新加载到最新版。新实现把比较放进数据库事务：若存储侧 updateTime 晚于调用方的 lastUpdateTime，立即抛出 StaleSessionError；调用方必须重新 getSession 后再决定是否重试。旧的 staleSession: reload 行为只作为已弃用兼容项保留。

相比“检测后自动刷新”，新增的不是一个异常类，而是一条写入前置条件：**陈旧句柄不得产生新事实**。PR 还增加跨包可识别的错误类型，并验证失败写入不会改变数据库或内存 Session。

### 工程价值、证据与局限

**来源结论**：正常 Runner 每次 invocation 都获取新 Session，并在顺序写入后更新 lastUpdateTime，通常无需改动；该变更针对并行调用方或长期持有 Session 的自定义集成。项目报告构建、类型检查、lint、38 个单元测试和 4 个集成测试通过。

**我的工程推断**：这可以直接抽象为 Agent 状态层的乐观并发控制。stateDelta 通常不满足交换律，遇到陈旧 revision 时自动“吸收最新版再写”会把冲突伪装成成功。更稳妥的 API 应携带 session_revision 或 expected_revision，失败后由上层重新读取、重验工具前置条件，再显式 rebase。

**局限**：当前判定仍以时间字段为依据，不等于严格单调版本号；重试是否安全取决于事件幂等性和外部副作用；数据库内的原子检查也不能自动覆盖已经发生的工具调用。兼容模式仍保留旧风险。

### 适用场景

- **Agent 会话与状态恢复**：恢复后的执行器用 checkpoint/session revision 做写入 fencing，避免旧 worker 复活后覆盖新状态。
- **工具确认与续跑**：批准到达前后都重验 revision；若计划或参数已变化，原 approval 不应继续消费。
- **SSE 与 UI 投影**：UI 提交状态修改若命中陈旧版本，应显示“已重新同步/需重试”，不能乐观地当作落盘成功。
- **多 Agent 编排**：多个 sub-agent 回写共享 Session 时，以条件写入或事件追加代替最后写入者获胜。

## 2. Microsoft Agent Framework：待审批计划成为可持久化、可恢复的 Gate 状态

**来源**：[microsoft/agent-framework #9797](https://github.com/microsoft/agent-framework/pull/9797)  
**合并日期**：2026-10-28  
**精读建议**：**必读**。它展示了 Gate 不应从聊天历史猜测，而应进入 workflow checkpoint 的权威状态。

### 核心变化

Magentic 编排在计划等待人工签核时，现在持久化 AwaitingPlanReview 状态。序列化 Session 再恢复后，工作流仍保持暂停；只有匹配的计划批准或修改反馈才能推进协调。等待期间到达的普通消息会被忽略并给出 workflow warning，缓冲的普通消息不会混入审批后的继续执行，而明确的 revision feedback 会被保留。

相比此前只在当前进程控制流中“等回复”，新增的是跨 checkpoint 的门控事实，以及对等待期间其他输入的分类处理。

### 工程价值、证据与局限

**来源结论**：PR 增加了流式、非流式和序列化恢复测试，覆盖“恢复后仍待审批”“批准后继续”“普通消息不误解锁”等情形；工作流测试套件 884 项通过。作者同时注明完整 solution 测试因磁盘耗尽未跑完。

**我的工程推断**：Gate 至少应持久化 gate_id、等待的响应类型、关联 plan revision/hash 与状态版本。批准动作是针对某个等待点的条件转换，不是普通 user message。若审批期间计划已被别处修改，应拒绝旧批准，保持同一 Run 在明确状态上等待，而不是创建一个语义不明的新 Run。

**局限**：实现聚焦 .NET Magentic；“忽略普通消息”是明确但偏强的产品策略，其他系统可能更适合拒绝、另开分支或入旁路队列；旧 checkpoint 的兼容与 schema 演进仍需应用自己验证。

### 适用场景

- **工具/任务门控**：把 waiting_for_approval 作为权威 Run 状态，审批请求和结果用 gate_id 关联。
- **确认后续跑同一 Run**：批准只解除当前等待点，继续原 checkpoint，不把批准文本当作新任务重新规划。
- **UI 投影**：审批卡片与普通输入框分轨；输入被忽略、排队或另开会话时给出明确反馈。
- **恢复与多 Agent**：协调器重启后仍知道哪个计划在等谁批准；sub-agent 不得绕过父级未决 Gate 提交最终结果。

## 3. LangGraph Python SDK：SSE 解码状态跨 chunk/重连保存，等待类接口统一退避

**主来源**：[langgraph #9477](https://github.com/langchain-ai/langgraph/pull/9477)  
**相关变更**：[#9462](https://github.com/langchain-ai/langgraph/pull/9462)、[#9481](https://github.com/langchain-ai/langgraph/pull/9481)、[#9482](https://github.com/langchain-ai/langgraph/pull/9482)  
**合并日期**：2026-10-28  
**精读建议**：**必读 #9477**；重连策略三项可选读。10 月 27 日收录的是空 id 的协议语义；今天新增的是解析器状态跨网络边界保存，以及重连失败本身的恢复闭环，不是重复报道。

### 核心变化

#9477 让 SSEDecoder 保留跨 HTTP chunk 和重连的状态：空 data 行、显式 data: null、无名事件、仅 CR 结尾、畸形 UTF-8 替换，以及上一连接留下的 last-event-id 都有对应测试。新的 has_data 区分“事件明确携带空/空值数据”和“根本没有数据”，避免合法事件被丢弃；重连时新 decoder 继承已解码游标，后续未带新 id 的事件仍沿用协议规定的最近 id。

配套变更把流式重连、runs.wait、join 和 cancel(wait=True) 的连接失败纳入带抖动的退避重试；但首次 POST 不重试，以避免重复创建 Run。若服务端未提供 Last-Event-ID，SDK 会警告可能存在事件缺口，而不是默默宣称连续。

### 工程价值、证据与局限

**来源结论**：解析测试覆盖 CR/LF/CRLF、空数据、畸形字节、游标继承等边界；重连对 429、5xx、传输异常与非 SSE 响应执行有限次数退避，成功收到事件后重置重试计数。可恢复流依赖游标避免丢事件；无游标流只能继续接收未来事件。

**我的工程推断**：应把链路拆成三种幂等边界：创建 Run 的请求、订阅事件流、按业务 ID 重放/收敛。创建 POST 不能因断线自动重发；订阅 GET 可以重连；UI reducer 仍应以事件游标加业务 item ID 去重，并在无游标重连时标记 gap_possible，再用权威快照校正。网络 chunk 从来不是业务事件边界。

**局限**：固定次数退避只是可用性策略，不提供 exactly-once；无 Last-Event-ID 时警告不能修复缺口；不可恢复流在退避期间仍可能丢事件；这些结论针对 Python SDK，其他语言实现需单独核验。

### 适用场景

- **SSE 流式收敛**：decoder 跨 chunk 保存字段缓冲，event 结束后才提交；重连继承 last-event-id。
- **Run 等待与取消**：wait/join/cancel(wait=True) 与普通 stream 使用同一重连状态机，避免控制面比数据面更脆弱。
- **状态恢复**：没有游标就把连接标为“可能有缺口”，拉取 Run/Items 权威快照再重建 UI。
- **sub-agent 汇合**：每个子流保留自己的 cursor 和业务序号；父级只在各子 Run 终态与快照一致后收敛。

## 今天可以尝试的两个工程验证

1. **做一次陈旧写入与旧批准联合故障注入**：同时启动两个 worker，在 A 写入新 revision 后，让 B 用旧 Session 和旧 gate_id 提交批准。期望结果应是两次条件写都失败，且外部工具不被再次调用。
2. **做一次无游标 SSE 重连演练**：在半个事件、显式空 data、畸形 UTF-8 和 reconnect 5xx 之间随机断链。验证 decoder 不提前出事件、等待接口按同一退避重连，UI 在缺少 Last-Event-ID 时进入 gap_possible 并从权威快照恢复。
