# 回路 · 2026-10-26

本期只收录一项，但它正好补上流式 Agent 最容易出现“最终状态正确、过程状态错误”的缺口：**工具失败被 runtime 接住并继续运行时，也必须在流中及时形成结果；结果的归属不能只看可重复的 `call_id`。**

这不是昨天“A2A 失败必须是结构化终态”的重复。昨天讨论远端子任务最终失败；今天讨论的是工具抛错后被 ToolNode 转换成可继续处理的 `ToolMessage`，以及 UI、重试和并发 Run 如何在最终 snapshot 之前获得正确结果。

## AG-UI / LangGraph：失败的工具调用也实时发送 TOOL_CALL_RESULT

- **来源**：[AG-UI PR #3202](https://github.com/ag-ui-protocol/ag-ui/pull/3202)
- **日期**：2026-10-25
- **精读建议**：**必读**

### 核心变化

**来源结论：** 成功工具调用会触发 `on_tool_end`，adapter 随即发送 `TOOL_CALL_RESULT`；但工具抛错时只触发 `on_tool_error`。如果 LangGraph 的 ToolNode 捕获异常、生成 `status="error"` 的 `ToolMessage` 并继续执行，旧 adapter 不会发送实时结果。错误只在最终 `MESSAGES_SNAPSHOT` 中出现，因此客户端在运行过程中看到的是一个没有结果的 tool call。

非流式模型下问题更明显：旧路径连该失败调用的 `START / ARGS / END` 都可能没有发出。

新实现分两阶段处理：

1. `on_tool_error` 只登记一次待匹配失败；
2. ToolNode 完成错误处理后，在 `on_chain_end` 从真实节点输出中取得最终 `ToolMessage`，复用成功调用的结果转换逻辑，发送 `TOOL_CALL_RESULT`。

这样流中的错误内容来自 ToolNode 配置的错误处理结果，而不是未经处理的原始异常；发送结果的 message ID 也与最终 snapshot 中的 ToolMessage 保持一致。非流式失败调用会先补发 `START / ARGS / END`，再发送结果。

### 新增的不只是“多发一个事件”

这次修复同时明确了三组容易混淆的语义。

**1. 结果归属绑定真实执行 Run**

待处理失败不再仅用原始 `tool_call_id` 索引，而是使用：

`parent_run_id + tool_call_id`

其中 parent run 是实际执行工具的 ToolNode run。这样可以避免：

- 不同轮次重复使用 `call_1` 时，旧结果匹配到新调用；
- 两个并发 child graph 都使用 `call_1` 时相互覆盖；
- 根图最终输出重复整条 thread 历史时，再次发送旧结果。

**2. 中断不是失败**

LangGraph 的 `GraphBubbleUp` 包括 interrupt，以及发往父图的控制流 Command。它同样经过 `on_tool_error`，但 ToolNode 会重新抛出，不会产生工具结果。新实现明确排除这类控制流事件，不再把等待用户输入或等待批准的调用误记为 failed。

**3. 重试恢复不能产生双结果**

如果某次尝试先失败，随后由 `wrap_tool_call` 重试成功，成功的 `on_tool_end` 会结算该调用并清除待处理失败；之后的 node output 不会再次发送失败结果。

### 工程价值与证据

这项改动使增量事件与最终 snapshot 更接近同一套权威语义：

- UI 不必等到 Run 结束才知道工具已经失败并被框架处理；
- 父 Agent 继续输出文本前，客户端已经收到该工具的结果；
- 恢复或重放时可以使用相同 message ID 合并流事件与 snapshot；
- 并发子图不会因为复用 call ID 而丢失或串错结果；
- 人工确认产生的 interrupt 不会被错误展示为工具失败。

PR 使用真实的离线 LangGraph、ToolNode 和 MemorySaver 增加测试，覆盖异常、参数校验失败、非流式模型、Command 错误处理、重试后成功、跨轮次重复 ID、中断以及并发 child graph 复用 ID。作者报告 Python integration 单元测试 859 项通过、1 项跳过；pytest 870 项通过、1 项跳过。这些是仓库测试结果，尚不是不同 adapter 或生产网络下的互操作验证。

### 局限

- AG-UI 当前的 `TOOL_CALL_RESULT` 还没有正式 error 字段，失败文本暂时仍放在 `content`；消费者不能仅靠事件类型区分成功与失败。
- 修复目前只进入 Python LangGraph adapter；PR 明确指出 TypeScript adapter 仍有相同缺口。
- 实现依赖 LangChain 事件中携带 `tool_call_id`；缺失时仍退回旧行为。
- `on_chain_end` 要等待 ToolNode 批次结束。并行 sibling 很慢时，已失败调用的结果也会延迟，但换来的是与最终 ToolMessage 完全一致。
- 这解决的是流式因果关系和去重，不提供外部工具副作用的 exactly-once。

### 适用场景与工程推断

- **Tool/Task Gate：** 将 `interrupted` 视为非终态。等待确认时保持调用 open，不生成失败结果；确认后应继续相同逻辑调用，并用 execution epoch 区分新的执行尝试。
- **SSE 收敛：** 工具事件顺序至少保证 `START → ARGS → END → RESULT`，随后才允许依赖该结果的 assistant text；最终 snapshot 使用同一 result/message ID 进行幂等合并。
- **状态设计：** 结果键应采用 `run/execution scope + call occurrence`，而不是裸 `call_id`。裸 ID 只能用于模型协议相关性，不能作为全局唯一键。
- **重试：** attempt-level failure 可以进入遥测，但对外只发布一次由 runtime 最终处理后的 result；如果需要展示每次尝试，应使用独立 `attempt_id`，不要复用终态结果事件。
- **sub-agent：** 并发 child graph 的相同 call ID 必须由 child run 或 node run 隔离；父级汇合根据执行作用域读取结果。
- **UI 投影：** 在协议增加 error 字段前，应用侧应保存 ToolMessage 的 `status` 或补充本地 outcome metadata，不要通过解析 `content` 文本猜测失败。

## 今天可以验证的两个问题

1. 构造两个并发子 Agent，都使用相同 `call_1`：一个失败并被 ToolNode 处理，另一个成功。验证 UI 收到两个独立结果，snapshot 重放后也不会覆盖或重复。
2. 对同一逻辑工具依次注入“中断等待确认”“第一次执行失败”“重试成功”：确认中断阶段没有伪造失败结果，最终只生成一次权威 `TOOL_CALL_RESULT`，同时 attempt 遥测仍完整。
