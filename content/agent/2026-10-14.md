## agent-browser v0.39.1：停止危险的重试

**发布日期：2026-10-13。精读判断：选读，实现 Tool Gate 时值得细看。**

### 核心变化

旧实现遇到 EOF、连接重置或读取超时时会重试。即使请求已经发送到 daemon，click、fill、eval 或导航仍可能再次执行，造成重复提交、输入或跳转。

新版按副作用可能发生的时间边界分类：

- 请求字节尚未发出：保留自动重试，确定没有产生副作用。
- 已发出请求，操作只读：可以重试。
- 已发出请求，且是写入或启动操作：停止重试，返回 outcome_unknown。

该状态进入 CLI JSON 和 MCP structuredContent，上层 runtime 可以先读取真实页面状态，再决定如何处理。

### 工程价值及局限

分布式执行需要表达第三种终态：

```text
succeeded
failed          # 确定没有完成
outcome_unknown # 可能完成，也可能未完成
```

修复只覆盖 CLI—daemon 边界，没有提供外部网站或工具的 exactly-once 保证，也没有自动完成结果对账。任意字节写出是一种保守判断，实际 daemon 可能尚未解析请求；没有幂等键的外部工具仍可能需要人工确认。

原简报记录关联 PR 描述了重复执行问题，合并前通过 19 项检查。此处保留发布说明入口，未恢复原聊天中缺失的具体 PR 链接。

## 工具、事件和 UI 应怎样表达

以下均为工程推断，可作为协议设计参考：

```text
prepared → dispatched
→ succeeded | failed_before_dispatch | outcome_unknown
→ reconciled_succeeded | reconciled_not_applied | manual_review
```

进入 outcome_unknown 后，不能当作确定失败自动创建一次新的语义执行。原批准是否允许再次尝试，需要结合审批契约、幂等键和对账结果判断。

如果下游支持 idempotency key，可使用原 attempt_id 对账或幂等重放；新的语义尝试则重新检查授权。

### SSE 与 UI 收敛

增加 tool.outcome_unknown、tool.reconciliation_started、tool.reconciled 等独立事件。UI 显示“结果待核实”，避免把它投影为普通失败并直接提供重试。

断线重连后，从权威 RuntimeState 恢复；不根据最后一条 SSE delta 猜测是否成功。

### Sub-agent 编排

子 Agent 的未知写结果向父 Run 冒泡。依赖该副作用的任务暂停，直到“可能已经发送邮件、提交表单或修改文件”的状态得到对账。

## 带回开发现场

1. 在工具完成副作用后、返回响应前断开连接，确认 runtime 不自动重复执行，也不错误标为 failed。
2. 检查 SSE / UI 的状态枚举是否能表达 outcome_unknown；若只有 running / success / failed，补上这个协议缺口。
