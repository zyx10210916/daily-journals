# 回路 · 2026-10-31

今天最值得关注的不是某个新框架，而是三处容易被“默认行为”掩盖的运行时边界被显式化了：**新发现的工具必须落入完整审批策略，消息与工具事件必须归属于真实执行图，Skill 的目标文件必须在沙箱内部落盘。** 三项变化分别作用于决策、观测和文件系统，却指向同一个设计原则：任何会改变 Run 状态的操作，都要绑定可验证的权威身份与作用域，不能依赖隐式 fallback 或继承上下文。

检索范围为 2026-10-30 09:16 至 2026-10-31 09:15（Asia/Shanghai）。本期未发现同一窗口内达到收录门槛的新论文；以下三项均为已合并的上游工程更新，且与 10 月 30 日已报道的重试事件屏障、checkpoint 恢复事务边界和 Durable Streams 回放机制不重复。

## 1. Microsoft Agent Framework：本地 MCP 审批策略新增显式默认值

**来源：** [Python: Add a default approval mode to MCP approval policies](https://github.com/microsoft/agent-framework/pull/9828)  
**合并日期：** 2026-10-30  
**精读建议：必读。** 这是动态工具系统里很关键的“策略完备性”修复，代码改动不大，但会直接影响未知工具能否绕过人工确认。

### 核心变化

**来源结论：** 过去本地 MCP 的 `MCPSpecificApproval` 只能分别列出 `always_require_approval` 与 `never_require_approval`；未列名的工具或 prompt 会落入框架原有的“无需审批”默认行为。更新新增可选的 `default: "always_require" | "never_require"`，解析顺序为：显式 always 列表、显式 never 列表、显式 default、旧的无需审批 fallback。这个 default 同样覆盖 MCP 在 `tools/list_changed` 后才发现的工具和 prompt。

同时，框架会在构造本地 MCP 工具时验证配置；若只配置 `never_require_approval` 而未给 default，会发出一次 `FutureWarning`，但本次仍保持旧行为。单个字符串形式的名称列表也被修正为一个完整名称，而不是可能被当作字符或子串模式处理。

这与 10 月 27 日已报道的“已注册工具强制 always_require 不能被工作流降级”不是同一问题：前者解决既有工具的策略优先级，本次解决未列名工具和运行中新增工具是否有策略覆盖。

### 工程价值、证据与局限

**来源证据：** PR 给出了动态发现、显式列表、默认值和旧行为兼容的测试，声明构建与单元测试通过。

**我的工程推断：** 对会动态变化的工具集合，“只列例外、不写默认值”本质上不是完整策略。生产环境应把未知工具默认设为 `always_require`，并把命中来源记录为 `explicit_allow / explicit_deny / policy_default / framework_fallback`，让 UI 能解释为什么出现或跳过确认。审批结果还应绑定 MCP server identity、工具名、schema/version 与规范化参数哈希；如果 rediscovery 后 schema 变化，旧批准不应继续生效。

**局限：** 此更新只影响本地 MCP；Hosted MCP 的默认机制没有统一。若使用方不设置 default，当前版本仍保留“未列名即无需审批”的旧行为。它也不是完整的属性策略系统，没有按参数风险、调用者或数据域组合规则。

### 适用场景

- **工具确认与同一 Run 续跑：** Run 在 Gate 暂停后继续执行时，按当前工具 schema 和 policy version 重新验证批准，而不是只凭旧的 tool name。
- **动态 MCP 会话：** 服务端发出 `tools/list_changed` 后，新工具自动落入 fail-closed 默认策略。
- **Sub-agent 编排：** 父 Agent 下发给子 Agent 的权限包应包含 default；子 Agent 不能因未列名而回退到框架隐式“免确认”。
- **UI 投影：** 在审批卡片上显示策略命中来源，区分显式规则、默认规则和兼容 fallback。

## 2. LangGraph：messages/tools 流事件使用真实 graph namespace

**来源：** [fix(langgraph): give messages and tools events the namespace of their graph](https://github.com/langchain-ai/langgraph/pull/9458)  
**合并日期：** 2026-10-30  
**精读建议：必读。** 这不是 UI 标签修饰，而是父图、子图和嵌套 task 之间的事件隔离规则；错误 namespace 会让前端收敛出错误的 Run 视图。

### 核心变化

**来源结论：** LangGraph 修正了 `messages` 和 `tools` 事件的 namespace，使事件归属于真正执行它们的 graph。更新覆盖四类边界：

1. `@task` 产生的嵌套 checkpoint 段不再被误判为 subgraph；此前可能在 `subgraphs=false` 时丢事件，在 `subgraphs=true` 时产生多余嵌套。
2. 节点内部启动、但拥有自己 `thread_id/checkpoint_ns/checkpoint_id` 的 graph 不再继承父图 handler 并把事件泄漏成父图事件；只有节点显式转发时才可见。
3. 同一节点依次启动多个 graph 时，handler 改为读取 loop 分配的当前 namespace，避免沿用第一个 graph 的旧值。
4. `push_message` 与其他流事件遵循同一 namespace 和 `subgraphs` 规则，并发送给所有符合条件的 handler，而不是只到第一个。

`stream_events(v3)` 也获得相同归属，因此此前缺失或错误归类的 token、tool call 会进入正确投影。

### 工程价值、证据与局限

**来源证据：** PR 新增了覆盖上述四类场景的测试，并说明除少数保护性用例外，这些测试在修复前的主分支会失败；未改写既有测试来迁就新结果。

**我的工程推断：** namespace 是流式状态的权威作用域，不只是展示字段。事件主键至少应包含 `thread/run/graph_namespace/call_id`；否则两个子图使用相同 call ID 时，父级 reducer 可能把 token、工具阶段或 completion 合并成同一实体。对于多 Agent UI，`subgraphs=false` 应被视为隔离边界；“节点显式把子图 stream 出去”则是受控桥接，而不是继承 handler 的偶然副作用。

**局限：** 这是事件归属修复，不提供 SSE 断线回放、全局序列号或 exactly-once 语义。依赖旧错误 namespace 的消费者可能需要迁移。Python 端的动态 namespace 规则仍较复杂，跨语言实现也需要单独做一致性测试。

### 适用场景

- **SSE 流式收敛：** 先按 graph namespace 路由，再在各作用域内按 call ID 聚合；不要只用全局 call ID。
- **Sub-agent 面板：** 父 Agent 与多个子 Agent 的 token/tool 事件分别投影，避免子图结果混入父图对话。
- **UI 投影：** `subgraphs=false` 时只展示当前图事件；显式桥接的子图事件保留原 namespace，并标记由哪个父节点转发。
- **状态恢复：** replay 时沿用持久化的 namespace，避免重连后把旧事件投到当前父图。

## 3. OpenAI Agents JS：本地目录 Skill 的目标写入收回 Docker 容器

**来源：** [OpenAI Agents JS PR #2091：Confine local-directory skill loading to Docker](https://github.com/openai/openai-agents-js/pull/2091)  
**合并日期：** 2026-10-30  
**精读建议：必读。** 它准确展示了一个常见隔离漏洞：工具最终在容器里运行，并不代表工具准备阶段的文件操作已经在沙箱内。

### 核心变化

**来源结论：** 过去加载本地目录 Skill 时，目标文件由宿主文件系统写入；更新改为通过 Docker archive copy 把文件复制到容器，目标路径的解析与写入都留在容器文件系统。实现复用 Docker CLI helper 的 archive stdin，不调用 shell copy 命令，并保留内容、权限和 ownership。

对于运行中的容器后来创建的 mount，Docker archive copy 无法访问，框架现在明确拒绝将目标写入这些路径，而不是悄悄回退宿主写入。测试还覆盖真实 Docker 下的普通加载、并发目录交换、二进制文件、空目录、权限、字面文件名、来源校验和复制失败；PR 报告 7,739 项测试通过、32 项跳过。

### 工程价值、证据与局限

**来源证据：** 除全套测试外，真实 Docker 用例会检查宿主 marker 未被改动，直接验证目标写入没有穿出容器；并发目录交换测试覆盖了较容易被遗漏的竞态。

**我的工程推断：** 沙箱边界必须包含“准备执行环境”的写入阶段。合理模型是：宿主只负责读取已授权的 Skill source，所有 destination path resolution 与 mutation 由 sandbox client 完成。每个 sub-agent 应拿到独立的容器内 Skill snapshot，并记录 snapshot digest 与 execution environment identity；子 Agent 提供的目标路径绝不能被宿主当作本地路径解释。

**局限：** 这是 Docker 专用加固；由于 archive copy 的限制，运行中创建的 live mount 目标会被拒绝。Skill 源文件仍由宿主读取并送入容器，更新也不判断 Skill 内容是否恶意；容器内代码执行仍需网络、凭据、资源和 syscall 等额外隔离。PR 没有给出复制性能基准。

### 适用场景

- **Sub-agent 隔离：** 每个子 Agent 使用独立容器和 Skill 副本，避免共享可写目录造成交叉污染。
- **Runtime 恢复：** checkpoint 只保存 Skill digest 和容器内目标，不持久化可被误解释为宿主路径的 destination。
- **并发编排：** 多个 Agent 同时交换或更新 Skill 目录时，验证容器目标的原子性与宿主不变式。
- **工具门控：** Gate 审批的不只是“加载哪个 Skill”，还应包含 source digest、目标沙箱和将获得的 mount/网络/凭据能力。

## 本期可尝试的工程验证

1. **动态工具 Gate 测试：** Run 启动后触发 `tools/list_changed`，加入一个未列名工具；默认策略设为 `always_require`。确认它会在原 Run 内进入审批态，UI 显示命中 default；随后改变工具 schema，验证旧批准因 schema hash 不匹配而失效。
2. **namespace × 沙箱隔离测试：** 同时启动两个子图，让它们使用相同 call ID 与相同 Skill 目标名；只显式转发其中一个子图的 stream。验证父 UI 不发生事件碰撞，断线 replay 后归属不变，并确认两个容器之外的宿主 marker 始终未变化。
