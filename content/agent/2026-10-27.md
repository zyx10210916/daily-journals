# 回路 · 2026-10-27

本期最值得关注的不是三个孤立修复，而是一条共同原则：**运行时不能把“默认值”或“存储返回顺序”误当成权威语义。**

- 工具声明为每次必须审批后，工作流层的缺省值或 `false` 不能把它降级；
- SSE 收到空 `id:` 后，重连游标必须被显式撤销，不能退回调用者最初传入的旧游标；
- 多个 checkpoint 时间戳相同时，恢复点要由谱系关系决定，而不是由保存顺序、目录顺序或数据库偶然返回的第一行决定。

检索窗口：2026-10-26 09:05 至 2026-10-27 09:25（Asia/Shanghai）。检索了主要 Agent runtime、协议与多 Agent 项目的主分支更新，并补查近期原始论文和官方工程来源；论文与报告侧没有发现同时满足时间窗口、新颖性和工程可迁移性要求的新增内容。下列三项均已合入各自仓库主分支，但不等同于已进入所有下游发行包。

## 1. Microsoft Agent Framework：注册工具的强制审批不能被工作流声明降级

- **来源**：[PR #9606](https://github.com/microsoft/agent-framework/pull/9606)
- **日期**：2026-10-26
- **精读建议**：**必读**

### 核心变化

**来源结论：** Python declarative runtime 过去只读取工作流 action 的 `requireApproval`。因此，即使函数在注册时标记为 `approval_mode="always_require"`，只要工作流省略 `requireApproval` 或显式写成 `false`，工具仍会未经审批直接执行。

修复后，执行器先从构造器工具表或 State 中的工具注册表解析实际工具，再按以下规则决定是否门控：

`action.requireApproval OR registered_tool.approval_mode == "always_require"`

换言之，任一层要求审批都必须停下来；较低安全级别的声明不能覆盖较高安全级别的工具策略。原有的 `ToolApprovalRequest → yield → handle_approval_response` 续跑路径保持不变。

### 工程价值、证据与局限

这项变化把审批从“调用点提示”提升为可组合的安全不变量：工具作者可以为支付、删除、发送或写入类工具声明最低审批要求，工作流编排者只能收紧，不能意外放宽。

PR 新增 11 个测试，覆盖 action 的省略、`false`、`true` 与批准/拒绝组合，以及构造器注册和 State 注册两种来源。作者报告旧实现有 6 个绕过用例失败，修复后 11 项全部通过；声明式测试套件未出现相对 main 的新增失败。证据是仓库级单元测试，不是跨进程恢复或多副本环境下的端到端验证。

局限包括：

- 当前规则只识别 `always_require`，还不是通用的策略格或风险评分合成器；
- 它保证“执行前暂停”，不自动保证审批响应与原始参数、用户、Run 或工具版本的强绑定；
- PR 复用现有续跑路径，没有单独解决审批后进程崩溃造成的外部副作用重复执行；
- 依赖下游升级到包含该修复的版本，主分支合入不代表所有部署已生效。

### 适用场景与工程推断

- **Tool Gate：** 把工具策略、租户策略、会话策略和单次 action 策略按“只可收紧”合成，推荐使用 `max(required_risk_level)` 或逻辑 OR，而不是让最近一层覆盖前面各层。
- **确认后续跑同一 Run：** 审批请求应持久化 `run_id + call_id + tool_version + canonical_args_hash + policy_version`；响应只解锁这个调用实例，不能变成同名工具的通用许可。
- **sub-agent：** 父 Agent 不能通过委派给子 Agent 绕过工具自身的最低审批策略；策略应随 capability 一起下传，并在实际执行节点再次校验。
- **UI 投影：** UI 展示“为何需要审批”时应保留策略来源，例如“工具强制”“工作流要求”“租户要求”，而不是压扁成一个布尔值。

## 2. LangGraph Python SDK：SSE 的空 id 是一次游标撤销

- **来源**：[PR #9402](https://github.com/langchain-ai/langgraph/pull/9402)；补充修复见 [PR #9440](https://github.com/langchain-ai/langgraph/pull/9440)
- **日期**：2026-10-26
- **精读建议**：**必读**

### 核心变化

**来源结论：** Python SDK 的 SSE decoder 有三处偏离规范：

1. 多个 `data:` 行直接拼接，没有插入换行，可能把 `[1` 与 `0]` 错解为 `[10]`；
2. 空 `id:` 没有清除重连游标，断线后仍发送旧 `Last-Event-ID`；
3. 流开头的 UTF-8 BOM 会混入第一个字段名，使首个事件丢失类型。

PR #9402 修正了解码规则；同日的 #9440 又补上两个更隐蔽的重连路径：

- 调用者最初传入的 `Last-Event-ID` 不能在流已经发出新 `id:` 后继续作为后备值；
- 只有空 `id:`、没有 event/data 的 block 也必须传递“清除游标”这一状态变化，不能被 decoder 当作无内容丢弃。

因此游标具有三态语义：尚未看到服务端 ID、持有非空服务端 ID、服务端已显式清空 ID。空字符串不是 `None` 的另一种写法，而是协议命令。

### 工程价值、证据与局限

工程上最关键的是避免“重连成功但数据悄悄重复”。PR 给出的复现场景是：客户端以游标 5 加入，服务端随后发送 6，再发送空 `id:`；旧实现断线后又从 5 重连，导致事件 6 重放。修复后，一旦服务端接管游标，调用者 header 会被大小写无关地移除；空 ID 后重连不再发送 `Last-Event-ID`。

测试覆盖同步与异步客户端、多行 data、BOM、带事件与独立出现的空 ID、调用者 header 的两种大小写，以及服务端新 ID 替换调用者游标。新增测试在旧 main 上失败。局限是：

- 这是传输层的规范一致性修复，不提供业务事件的 exactly-once；
- 空 ID 后无游标重连可能导致更大范围重放，应用层仍需事件幂等；
- #9440 晚于当日 LangGraph 1.2.18 发布提交，不能据此假设该补充修复已进入 1.2.18；
- 多行 `data:` 改为按规范插入换行后，过去依赖错误拼接才可解析的 payload 会暴露为解码错误。

### 适用场景与工程推断

- **SSE 流式收敛：** 将 transport cursor 与业务 `event_id` 分离。前者决定从哪里重连，后者用于 reducer 去重；不要让 `Last-Event-ID` 兼任全局业务主键。
- **权威状态：** reconnect cursor 是带来源的状态机：`caller_seed → server_owned(value) → server_cleared`。一旦进入 server-owned，旧 seed 不得复活。
- **UI 投影：** 重连后允许重复投递，但 reducer 必须按 `run_id + event_id` 幂等；snapshot 或 terminal event 负责最终收敛。
- **sub-agent：** 多个子 Run 共用一条 SSE 时，每个事件仍应携带逻辑 Run 作用域；传输游标只能恢复字节流位置，不能替代子 Run 归属。

## 3. Microsoft Agent Framework：同时间戳 checkpoint 用谱系而非枚举顺序定“最新”

- **来源**：[PR #9261](https://github.com/microsoft/agent-framework/pull/9261)
- **日期**：2026-10-26
- **精读建议**：**选读**；做持久化、恢复或并行工作流时升为必读

### 核心变化

**来源结论：** `get_latest` 过去只对 timestamp 取 `max()`。同一 superstep 边界的 checkpoint 可以共享时间戳，系统时钟分辨率也可能让不同边界碰撞；此时结果取决于保存顺序、文件枚举顺序或后端返回顺序，Run 可能无报错地恢复到已经被后继 checkpoint 取代的旧状态。

新选择器先保留最大时间戳组，再利用 `previous_checkpoint_id` 排除已被同组后继引用的 checkpoint，选择谱系叶节点。若仍有多个互不继承的叶节点，则按 `checkpoint_id` 取稳定最大值，至少让选择可重复。修复覆盖内存、文件、Azure Cosmos 与 Foundry Hosting 存储；Cosmos 改为一次按时间倒序的查询，读取完整的最新时间戳组后立即停止，避免“先查 MAX、再查记录”之间的并发竞态。

### 工程价值、证据与局限

这使“latest”从存储偶然性变成可解释的恢复规则。测试覆盖父—子—孙同时间戳、正反保存顺序、互不继承的叶分支、Cosmos 分页以及查询期间并发保存/删除。PR 描述中，早期核心用例在旧实现的 4 个组合中有 3 个失败，另 1 个只是碰巧通过。

局限仍然重要：

- 对同时间戳的并列分支，按 `checkpoint_id` 选最大只是确定性 tie-breaker，不代表业务上“正确的胜者”；
- 线性 `previous_checkpoint_id` 足以描述单链后继，但不能表达合并提交的多个父节点；
- “最新时间戳组”需要完整读取；异常大的同时间戳组会增加存储开销；
- 该规则没有替代 fencing token、generation 或 compare-and-swap，不能单独阻止旧 worker 在恢复后继续写入。

### 适用场景与工程推断

- **状态恢复：** 每个 checkpoint 至少持久化 `checkpoint_id`、`previous_checkpoint_id`、`run_generation` 与逻辑 step；timestamp 只用于检索和观察，不应单独决定权威顺序。
- **工具确认与续跑：** gate 前后的两个 checkpoint 如果时间相同，谱系应明确“批准后状态”继承“等待批准状态”；恢复时不能因枚举顺序回到 gate 前并再次发起同一副作用。
- **多 Agent 汇合：** 并列分支不应偷偷用 ID 决定语义胜负。汇合节点应记录已消费的 child checkpoint 集合，并生成新的 merge checkpoint。
- **并发控制：** 恢复时发放新的 generation/fencing token；旧 generation 的迟到事件和 checkpoint 写入必须拒绝或隔离。

## 今天可以尝试的两个工程改进

1. **把“缺省、显式否定、强制要求”分成三态。** 对审批策略和 SSE 游标分别做属性测试：低层显式强制不能被高层缺省/false 降级；服务端显式清空游标后，调用者旧值不能复活。
2. **建立恢复不变量测试。** 在同一毫秒内写入 gate 前、gate 后和工具结果三个 checkpoint，并打乱保存与读取顺序；验证始终恢复到谱系叶节点，同时用 generation 拒绝旧 worker 的迟到写入。
