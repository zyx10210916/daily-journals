# 回路 · 2026-10-23

## 本期最值得关注

过去 24 小时的三项更新都在修同一种错误：**把稳定的逻辑 ID 当成了唯一的运行时身份。**

- 同一个 background task ID 可以被 continuation 复用，但旧 waiter 只能结算它真正等待的那次 execution。
- 同一个 parallel worker 包含多个 item，失败重试应属于 item，而不是重新执行整个批次。
- 同一个 tool call ID 可能跨轮复用；恢复后的消息必须按实际调用实例重新配对，不能只按字符串 ID 就近归并。

这比新增一种 Agent 抽象更值得带回工程现场，因为它直接决定了续跑、重试和流式恢复是否会覆盖较新的状态或重复外部副作用。

检索窗口：2026-10-22 09:38 至 2026-10-23 09:38（Asia/Shanghai）。以下均为 2026-10-22 合入主分支的更新，尚未按稳定版能力评估。

## 1. Microsoft Agent Framework：后台完成等待绑定 execution，而不是 task ID

- **来源**：[PR #9442](https://github.com/microsoft/agent-framework/pull/9442)
- **日期**：2026-10-22（合入 main）
- **建议**：**必读**

### 核心变化

问题发生在 background task 的 continuation：旧 execution 完成后，一个 waiter 已经被唤醒，但尚未执行结算；此时另一调用方用相同 task ID 启动了 continuation。旧代码会重新按 ID 查询当前任务，于是可能把新的 continuation 当成自己等待的旧 execution：运行中的 continuation 会触发 InvalidStateError，已经结束的 continuation 甚至可能被旧 waiter 提前结算或报告。

修复后，waiter 保留从原始 wait set 中选中的具体 asyncio Task 对象。只有 runtime 中该 ID 仍映射到同一个对象时，才允许删除引用和持久化结果；若 ID 已指向新的 continuation，旧 waiter 只报告旧 execution，不覆盖新状态。

### 工程价值、证据与局限

**来源结论**：PR 新增 12 组 continuation 竞争组合和 1 个双 waiter 用例，覆盖旧 execution 成功、失败、取消，以及 continuation 运行中、完成、已结算、失败等组合。合并页面显示 58 项检查通过。

**我的工程推断**：task_id 是逻辑槽位，execution_id 或对象身份才是可结算的实体。任何完成回调都应做 compare-and-set：

- 读取时保存 execution revision；
- 写回时验证 task_id 仍指向同一 revision；
- 陈旧回调可以记录事实，但不得修改 current pointer。

局限是该修复针对单进程 asyncio runtime。跨进程 worker、消息队列重复投递和数据库并发仍需要持久化 execution_id、版本号或 fencing token。

### 适用场景

- **Sub-agent 续跑**：父 Agent 对同一 task 发 follow-up 时，旧完成事件不能覆盖 continuation。
- **状态持久化**：task 表保存 current_execution_id，execution 单独建表；完成写入使用条件更新。
- **UI 投影**：旧 execution 的结果可展示为历史，但 task 卡片的当前状态只接受 current execution。
- **工具确认**：批准也应绑定具体 execution/action digest，不能因为 task ID 相同而自动继承。

## 2. Google ADK：并行 worker 只重试失败 item，不重跑整个批次

- **来源**：[提交](https://github.com/google/adk-python/commit/a9714eceb6b012cd68d7701467acdb098a6befc8)
- **日期**：2026-10-22（合入 main）
- **建议**：**必读**

### 核心变化

此前 parallel worker 的 retry_config 留在 worker 层。一个 item 失败会使整个 worker 重试，仍在运行的 sibling 被取消，已经完成或正在执行的 item 可能再次运行。对同时在 worker 和 item 保留策略的 Node 子类，持续失败的 item 甚至可能执行 max_attempts 的平方次。

修复把 retry_config 下沉到被包装的 item node：失败 item 原地重试，其他 sibling 继续运行；NodeRunner 看到 item failure 后不再额外重试整批。文档同时明确区分 item retry、worker timeout 和外层 node retry 的作用域。

### 工程价值、证据与局限

**来源结论**：新增测试覆盖不同 worker 声明方式、重试次数不相乘、model_copy 清除或替换策略、Agent clone 保留 parent_agent，以及 item 失败不会重跑整批。

**我的工程推断**：重试预算必须属于最小可独立重放单元。对并行 sub-agent，至少需要 child_execution_id、attempt 和 side_effect_key；否则一次局部瞬态错误可能放大成整批重复写入。

限制仍然存在：item 最终耗尽重试后，worker 依旧 fail-fast 并取消未完成 sibling；外层 node retry 或 worker 级 timeout 仍可能让整批重跑。框架没有替应用提供外部副作用 exactly-once。

### 适用场景

- **多 Agent 并发**：研究、检索、批量生成等 fan-out 任务按 child item 独立重试。
- **结果汇合**：join 以输入 index 和 child_execution_id 收敛，不能按完成顺序直接覆盖。
- **状态恢复**：已完成 item 从历史重放，失败 item 获得新的 attempt；整批 timeout 需单独定义。
- **外部写操作**：每个 item 使用独立幂等键，并记录副作用是否已确认。

## 3. AG-UI：在下一 Run 的 wire input 中重建 tool call/result 因果顺序

- **来源**：[PR #3143](https://github.com/ag-ui-protocol/ag-ui/pull/3143)
- **日期**：2026-10-22（合入 main）
- **建议**：**必读**

### 核心变化

AG-UI 之前已经修复 MESSAGES_SNAPSHOT 合并后的工具结果顺序，但旧历史、initialMessages 和 onRunInitialized 仍可能形成：

assistant(tool_call) → assistant(text/reasoning) → tool(result)

一些 provider 会拒绝这种历史；当后端 checkpoint 丢失、只能从客户端消息重建状态时，也可能静默丢弃无法配对的结果。

新实现会在 runAgent/connectAgent 发出下一 Run 前，对**发送副本**重新配对 tool call 与 result，但不修改 Agent 自己保存的消息历史。reasoning 被视为不切断配对关系；若必须移动 result，也避免把它插进 reasoning 与其所属消息之间。

### 工程价值、证据与局限

**来源结论**：PR 报告 Mastra 687 项、LangGraph TS 908 项和 AG-UI client 1291 项测试通过；还对 20 万组随机历史比较新旧算法。在一个重复 call_0 的 2 万条消息样本上，作者报告处理时间约从 208 ms 降至 3 ms。这些是 PR 作者的仓库内测试结果，不是独立基准。

**我的工程推断**：这里值得借鉴的是“展示状态与传输规范化分离”。UI 可以保留原始事件和 reasoning 排布，发起续跑时则从权威历史派生符合 provider 因果约束的 wire projection；不要为了修请求而偷偷改写用户看到的历史。

局限是后续 middleware 或原地修改 input.messages 仍可能再次破坏顺序；重复 result 仍可能被配到更早的同 ID 未决调用。因此生产实现最好同时使用 call occurrence 或 run-scoped call key，而不是只用 call_id。

### 适用场景

- **SSE 断流与重载**：客户端从 snapshot/event log 恢复后，在下一 Run 前做确定性 wire normalization。
- **UI 投影**：原始消息、activity 和 reasoning 继续服务展示；provider input 是独立派生视图。
- **工具续跑**：tool result 必须紧邻实际发出它的 call occurrence，不能仅按字符串 ID 关联。
- **状态恢复**：服务端 checkpoint 缺失时，可从规范化客户端历史重建，但应记录修复告警而不是静默吞结果。

## 可以立即尝试的两项改进

1. **统一引入 execution identity**：task、gate、tool call 和 sub-agent child 都保存 logical_id、execution_id、attempt、revision；异步回调写回时使用 current_execution_id 条件更新。
2. **做一次重试与恢复故障注入**：让并行 item 在外部写入后、结果持久化前失败，同时让旧 waiter 延迟返回并启动 continuation；验证不会重跑成功 sibling、不会覆盖 continuation，也不会在 UI/下一 Run 中丢失 tool result。
