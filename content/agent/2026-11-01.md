# 回路 · 2026-11-01

今天三项更新都在修补“信息跨过运行时边界后被静默丢失或误归类”的问题：**MCP 工具目录变化要进入应用控制面，模型隐藏 thought 不能混入可检索长期记忆，Live usage 即使与文本分开发送也必须收敛到正确调用。** 它们共同提示：Agent runtime 不应把 SDK 默认处理、原始 transcript 或流式 chunk 直接当作权威状态，而要为控制信号、可见内容和计量事件分别定义归属与合并规则。

检索范围为 2026-10-31 09:15 至 2026-11-01 09:04（Asia/Shanghai）。已核查主要 Agent runtime、协议、多 Agent 项目在该窗口内的主分支更新与官方资料，并补查新论文；没有发现同时满足时间窗口、新颖性与工程可迁移性要求的新论文。窗口内其他项目主要是文档同步、教程修正或常规维护，因此本期三项都来自 Google ADK，但关注的是三个不同的运行时边界。

## 1. Google ADK：McpToolset 允许应用接收 MCP server notifications

**来源：** [feat(mcp): allow callers to receive server notifications](https://github.com/google/adk-python/pull/7689)  
**落地主分支日期：** 2026-10-31  
**精读建议：必读。** 它把 `tools/list_changed` 从 SDK 内部信号提升为应用可参与处理的控制面输入，是动态工具、审批策略和 UI 同步的前置能力。

### 核心变化

**来源结论：** 此前底层 MCP SDK 支持 `message_handler`，但 ADK 的 `McpToolset` 没有把它暴露到公共 API，应用无法通过标准构造路径消费 `notifications/tools/list_changed` 等 server notification。更新为 `McpToolset`、`MCPSessionManager` 和 `SessionContext` 增加可选 `message_handler`，并将它传递到两条 `ClientSession` 构造路径；未设置时仍使用 MCP SDK 默认处理。

该能力覆盖 stdio、SSE 和 Streamable HTTP，并验证 session 复用与重连后仍能收到通知。重要的是，PR 明确指出：**暴露 notification 不等于自动完成工具列表缓存失效**，刷新和重新建模仍由应用负责。

### 工程价值、证据与局限

**来源证据：** MCP 子系统在 MCP 1.30.0 与 2.3.0 下各有 659 项测试通过；外部分支的 Linux 全量矩阵在 Python 3.11–3.14 报告约 2.1 万项测试通过。真实 MCP server 的确定性 E2E 覆盖三种 transport、session reuse 和 reconnect，共报告 9 个场景通过。主分支随后通过 Copybara 集成了该变更。

**我的工程推断：** `tools/list_changed` 应被当作“权威目录可能变化”的失效提示，而不是直接修改本地工具状态的事实事件。合理处理流程是：收到 notification → 重新拉取完整 tools list → 计算 toolset revision/schema hash → 原子替换目录 → 重新评估尚未消费的审批和工具调用。若同一 Run 正停在 Gate，目标工具 schema 或风险策略变化后，旧 approval 应失效。

**局限：** 更新只提供回调通路，没有定义缓存刷新、通知去重、顺序保证或 approval 失效协议。notification 与在途工具调用也可能并发；如果应用在 callback 中直接修改共享目录，仍可能出现半更新状态。测试没有证明跨进程消息总序或 exactly-once。

### 适用场景

- **动态 MCP 与工具门控：** 新增、删除或变更工具后，重算策略覆盖和审批要求。
- **确认后续跑同一 Run：** 恢复前比较 `approved_tool_revision` 与当前 `toolset_revision`，不一致则保持原 Run 暂停并重新请求确认。
- **UI 投影：** notification 只触发“目录待刷新”；完整拉取成功后再发布新的工具面板 revision。
- **状态恢复：** checkpoint 保存已使用的 toolset hash，重连时先同步目录，再恢复未完成调用。

## 2. Google ADK：Firestore 长期记忆排除模型 thought parts

**来源：** [fix(firestore): keep thought parts out of FirestoreMemoryService](https://github.com/google/adk-python/pull/7831)  
**落地主分支日期：** 2026-10-31  
**精读建议：选读；使用长期记忆时必读。** 改动局部，但“可检索记忆不是原始 transcript”这一边界非常值得迁移。

### 核心变化

**来源结论：** 旧的 `FirestoreMemoryService` 会从事件的所有 part 构建关键词并保存内容，其中包括模型的 hidden thought。结果是：只在 thought 中出现的词也可能命中搜索，`load_memory` 或 `PreloadMemoryTool` 又会把这些内部推理重新喂给模型；只有 thought、没有可见文本的事件也会形成记忆文档。

更新后：

1. 写入时仅使用非 thought part 生成关键词和存储内容；
2. thought-only 事件不写入；
3. 搜索时也过滤历史文档中的 thought part，避免旧数据继续被返回；
4. `thought=False` 或未标记的普通内容保持不变。

该行为与 ADK 的 in-memory、Vertex RAG 和 SQLite memory service 对齐。

### 工程价值、证据与局限

**来源证据：** 新增测试覆盖写入过滤、thought-only 跳过和历史文档读取清洗；Firestore 与 memory 相关测试共 256 项通过，类型检查和变更文件的 pre-commit 检查通过。

**我的工程推断：** 长期记忆应是带有明确 inclusion policy 的派生投影，而不是把整个事件对象原样序列化。建议为可持久内容记录 `visibility`、`provenance` 与 `memory_policy_version`；写入端做最小化，读取端继续做防御性过滤，以兼容旧数据。Sub-agent 的内部 reasoning 也不应因为汇总或共享记忆而自动暴露给父 Agent。

**局限：** 测试使用 mock Firestore，没有真实 Firestore/emulator E2E。读取过滤能防止旧 thought 被返回，但不会自动删除已经物理存储的数据；若涉及数据治理或保留策略，仍需离线迁移。它也只处理显式标记为 thought 的 part，无法识别被模型错误放入普通文本字段的隐性推理。

### 适用场景

- **Agent 会话与长期记忆：** 只把用户可见事实、明确结论和允许保留的工具结果投影到 memory。
- **状态恢复：** checkpoint 可保存执行所需内部状态，但恢复后写入长期记忆时仍执行 visibility policy。
- **Sub-agent 上下文汇合：** 父 Agent 接收结构化结果和证据，不继承 child 的隐藏思考。
- **UI 投影：** 历史搜索、记忆管理页和导出内容使用同一可见性过滤规则。

## 3. Google ADK：Live usage 事件与内容分离时仍能正确收敛

**来源：** [fix(eval): preserve live usage without extra inference calls](https://github.com/google/adk-python/pull/7323)  
**落地主分支日期：** 2026-10-31  
**精读建议：选读。** 若在做流式评测、成本统计或运行时观测，值得精读；普通 Agent 业务可以只吸收其事件合并原则。

### 核心变化

**来源结论：** Gemini Live 可能把 token usage 与响应内容放在不同事件中发送。旧的 evaluation conversion 会丢掉这些单独 usage report；若简单把每个 report 都保留为新的 model event，又会错误增加 inference count。

更新后会保留携带 usage 的事件，包括空内容和非文本内容，并尝试将独立 usage 合并到兼容的 model event。匹配条件包括相同 author、model 与 Live connection identity；已有 usage 不被覆盖，输入事件不被原地修改。找不到兼容事件的 usage 仍会独立保留，并按它代表的一次模型调用计数，而不是静默丢弃。

### 工程价值、证据与局限

**来源证据：** 216 项相关测试通过；构建 wheel 后在独立环境运行的 19 项回归测试通过。用例覆盖 usage 在内容前、内容后、跨多个 chunk、非文本内容、连接或作者不匹配及输入不可变性。全量测试仍存在 54 个基线失败，作者逐项在未修改的 main 上复现；没有连接真实 Gemini 服务验证远端事件顺序或计费语义。

**我的工程推断：** usage、文本和终态属于同一逻辑调用的不同投影，不能用网络 chunk 数推断 inference 数。运行时应以 `run_id / logical_call_id / model / connection_id` 聚合，并允许已完成文本在稍后收到 usage 时产生一个新的 telemetry revision。UI 可以先显示“用量待结算”，再更新成本，而不要为了保持单次渲染而丢掉迟到数据。

**局限：** 该修复针对评测转换，不等于在线账单的权威计费协议；匹配仍依赖 author、model 和 connection identity，若上游缺少稳定 logical call ID，复杂并发下仍可能歧义。固定测试无法证明生产网络中的所有乱序情况。

### 适用场景

- **流式事件收敛：** 内容、usage、tool timing 和 terminal event 分别到达时，以逻辑调用 ID 合并，而非按 chunk 数计数。
- **Evaluation：** inference count 与 token usage 分开计算；usage report 不是额外模型调用。
- **UI 投影：** 终态消息允许后续补充成本 revision，不重放或复制正文。
- **多 Agent 编排：** 每个 child Run 独立聚合 usage，再由父级按 child/run 维度汇总，避免跨连接误合并。

## 本期可尝试的工程验证

1. **工具目录变更 × 旧审批测试：** 在同一 Run 等待工具确认时发送 `tools/list_changed`，让工具 schema 或风险等级发生变化。验证 notification 只触发全量刷新；刷新成功后 toolset revision 原子前进，旧 approval 被拒绝，外部工具没有执行。
2. **三路迟到事件测试：** 让可见文本、usage 和 hidden thought 以不同顺序到达并经历一次重连。验证文本只落一次、usage 最终归到正确 logical call、thought 不进入长期记忆，刷新 UI 后三种投影仍保持一致。
