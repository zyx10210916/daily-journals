# 回路 · 2026-10-25

今天三项更新共同指向一个很实用的原则：**跨 Agent 边界时，控制状态不能退化为普通文本，临时上下文也不能依赖模糊的“共享会话”直觉。**

最值得关注的是 Google ADK 对 A2A 失败语义的修复：远端 Task 的 `failed` 终于会变成可供 runtime、UI 和父 Agent 判断的错误事件，而不是混进对话历史。另两项分别补清了嵌套 Agent 的临时状态作用域，以及 tool-heavy Run 中 checkpoint 写入的并发边界。

检索窗口：2026-10-24 09:19 至 2026-10-25 09:49（Asia/Shanghai）。仅收录窗口内进入主分支或完成合并、且与此前日报不重复的更新。

## 1. Google ADK：失败的 A2A Task 不再伪装成普通对话内容

- **来源**：[主分支提交](https://github.com/google/adk-python/commit/25d191710985371dfb93a131f2fa797734850952)
- **日期**：2026-10-24
- **精读建议**：**必读**

### 核心变化

**来源结论：** 此前，远端 A2A Task 即使进入 `failed`，ADK 仍可能只提取其状态消息并生成普通 `Event.content`。错误文本随后进入会话历史，父 Agent 或下一位 Agent 会把它当成正常对话，而不是一次失败的子任务。

修复覆盖非流式 `Task` 与流式 `TaskStatusUpdateEvent`，并同时处理旧版和新版 RemoteA2aAgent 路径：

- 为失败事件设置稳定的 `error_code=A2A_TASK_FAILED`；
- 将远端状态文本放入 `error_message`，无文本时使用通用错误消息；
- 若远端已经提供更具体的错误码，则保留原值；
- 即使失败 Task 没有消息正文，也生成最小错误事件，不再静默丢失终态；
- 通过兼容层识别不同 A2A SDK 版本的 failed 状态。

相比仅在 UI 上显示“远端失败”，这次修复恢复了协议层的对称性：A2A 的 terminal failure 进入 ADK 后仍然是控制面失败，而不是数据面消息。

### 工程价值、证据与局限

**工程价值：** 父 Agent 可以停止后续步骤、选择重试或转交其他 Agent；UI 可以关闭对应 child run；持久化层也能留下明确失败终态。它避免了最危险的一类状态污染——失败事实被重新送进模型，并被模型解释成远端 Agent 的正常回答。

提交同时增加了有消息、无消息、自定义错误码、流式与非流式等回归测试。相关 PR 报告 A2A 单测 447 项通过、45 项跳过，RemoteA2aAgent 测试 174 项通过；这些是仓库测试结果，不是跨实现互操作评测。

**局限：** `A2A_TASK_FAILED` 仍是较粗的框架级错误码；不同远端 Agent 的可重试性、部分结果和补偿要求需要额外元数据。修复也没有提供 exactly-once、自动重试或跨服务取消传播。

### 适用场景与工程推断

- **多 Agent 编排：** 将 `failed/canceled/rejected/input-required` 作为结构化终态映射，禁止降级为 assistant text。
- **SSE 流式收敛：** 收到失败状态后，先落库 child terminal event，再关闭 UI 投影；迟到的文本或 artifact 只能进入审计流，不能把子任务重新变成 running。
- **状态恢复：** 保存 `remote_task_id + context_id + child_execution_id + terminal_state + error_code`，恢复时不依赖最后一条消息推断成功或失败。
- **结果汇合：** 父 Agent 的 join 条件依据子任务终态，而不是“是否收到过内容”；部分 artifact 与失败状态应允许同时存在。

## 2. Google ADK：AgentTool 获得一次调用范围内的临时状态投影

- **来源**：[主分支提交](https://github.com/google/adk-python/commit/12c7bed7661ccf942f0f6d3b62bed22a23ea0a85)
- **日期**：2026-10-24
- **精读建议**：**必读**

### 核心变化

**来源结论：** `AgentTool` 包装的 Agent 虽然被描述为当前 invocation 的一部分，实际上却会创建嵌套 session。旧实现把调用者状态交给 `create_session`，但 session 创建会丢弃所有 `temp:` key，导致被包装 Agent 的 instruction、callback 和工具读取不到临时值，必填模板甚至直接抛出 `KeyError`。

修复将持久状态和临时状态拆开：

- 普通 key 仍通过嵌套 session 初始化；
- `temp:` key 通过 nested runner 的 `state_delta` 注入，只在该次 invocation 内生效；
- ADK 自身的 `temp:_adk...` 内部 key 不向下传递；
- 字典、列表和集合做浅拷贝，减少子 Agent 原地修改对调用者的直接影响；
- 传递是单向的，子 Agent 新写入的临时状态不会自动回流父 Agent。

相比“父子 Agent 共享上下文”的笼统描述，这次给出了更具体的边界：**调用者到被调 Agent、单次 invocation、非持久化、默认不回写。**

### 工程价值、证据与局限

**工程价值：** 请求级 trace、候选集、临时约束和只用于本轮的用户输入，可以在嵌套 Agent 中保持一致，而不会被错误地写进长期 session。新增测试覆盖 instruction、optional instruction、callback、内部工具、SequentialAgent 和 input schema 等读取路径；提交说明完整 tools 测试为 3136 项通过。

**局限：** 浅拷贝不是深隔离，容器内部的嵌套可变对象仍可能共享引用。单向不回写也意味着子 Agent 不能靠修改临时状态向父级返回结果；结果仍应走显式 tool result 或事件协议。它是可见性边界，不是安全权限边界，不应把审批令牌或高权限凭据整包下传。

### 适用场景与工程推断

- **sub-agent 上下文：** 为每类字段声明 `scope / direction / copy / persistence`，例如 `invocation + parent→child + shallow-copy + ephemeral`。
- **Tool/Task Gate：** 可下传 `gate_id` 和动作摘要用于相关性校验，但真正授权仍从权威状态读取；临时上下文中的布尔值不能直接充当执行能力。
- **状态持久化：** 临时状态不进入 checkpoint 时，恢复逻辑必须能重新派生或明确报过期，不能假设断线后仍存在。
- **结果汇合：** 子 Agent 的输出通过结构化 result 返回；不要把共享可变 state 当作隐式返回通道。

## 3. Deep Agents：checkpoint 写入采用“进程内排队 + 跨进程锁”

- **来源**：[Deep Agents PR #7245](https://github.com/langchain-ai/deepagents/pull/7245)
- **日期**：2026-10-25（Asia/Shanghai；合并时间为 2026-10-24 21:25 UTC）
- **精读建议**：**选读**

### 核心变化

**来源结论：** 同一会话的多个 checkpoint 写入原本直接竞争文件锁，未取得锁的 writer 每 10 ms 轮询一次。工具调用密集时，这会把本地 SQLite saver 的锁等待和线程切换放大到每个 Agent step。

新实现增加两层协调：

1. 同一 event loop 内，按会话使用 `asyncio.Lock` 排队，不再轮询文件锁；
2. 跨进程仍保留原有文件锁与 ownership token 校验。

同时缓存 ownership 文件路径，并把锁获取与 owner 校验放在同一受保护过程里。测试让八个本地 writer 并发写同一 thread，确认临界区峰值为一且没有非零 sleep polling。

### 工程价值、证据与局限

**来源证据：** 团队用 fake model 连续执行 50 次 `write_todos`，报告受 ownership 保护的 SQLite saver 单次工具调用开销由 209–308 ms 降至 22–43 ms；四个并发 writer 的隔离 guard 由 36.4–36.9 ms 降至 3.4–3.7 ms。

**局限：** 这是团队在负载机器上的局部 benchmark，不代表真实模型调用的端到端提升。它优化的是单机 SQLite 与同一 event loop 内的竞争，不解决多机数据库事务、重复消息或 checkpoint 的业务幂等。实现仍依赖跨进程文件锁，不能把本地 `asyncio.Lock` 当作分布式锁。

### 适用场景与工程推断

- **Agent runtime：** 高频工具事件和 token/step checkpoint 不应各自忙轮询同一持久化锁；先在进程内排队，再进入真正的跨进程 fence。
- **状态恢复：** ownership 必须在取得最终写锁后再次验证，避免 writer 排队期间 thread 已转移给新 owner。
- **工具确认续跑：** approval response、tool result 与新 Run 若同时触发写入，应串行提交到同一 thread revision，并在提交时校验 execution/owner。
- **性能观测：** 分开记录 queue wait、file-lock wait、serialize 和 SQLite commit，避免把 checkpoint 延迟误判成模型首 token 延迟。

## 今天可以验证的两个问题

1. **做一次“失败文本污染”回放。** 让远端 Agent 在产生部分 artifact 后进入 failed，检查父 Agent prompt、UI、持久化事件和 join 逻辑：部分结果可以保留，但失败文本不能以正常 assistant message 进入下一轮。
2. **写一份上下文传递矩阵。** 对父 Agent、AgentTool 和异步 sub-agent 的每个字段标注作用域、方向、复制方式、持久化与权限含义；再在 checkpoint 写入排队期间切换 owner，验证旧 writer 会在最终提交前被 fence 掉。
